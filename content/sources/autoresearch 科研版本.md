

• 这个想法最大的启发，不是“AI 会做研究”，而是：

  很多看似只能靠人类直觉推进的工作，先可以被重写成一个可执行闭环。

  我觉得最重要的启发有这几个：

  - 真正的杠杆不在答案，而在闭环。
    一次漂亮回答没那么重要；更重要的是能不能形成 提出假设 -> 修改系统 -> 真实运行 -> 读结果 -> 保留/丢弃 的循环。
  - 未来最值钱的能力，可能不是亲手做研究，而是设计研究系统。
    人的角色从“做每一步”变成“定义问题、边界、指标、预算、模板、评价函数”。
  - prompt 不是核心，环境才是核心。
    没有代码执行、结果协议、客观指标，再聪明的模型也只是会说。
    一旦有了环境和 evaluator，普通模型也能开始积累进展。
  - 复杂智能，常常来自简单机制的长期[[复利]]。
    autoresearch 很打动人的地方就在这：它不是先做一个巨型研究帝国，而是先把最小闭环做稳。这个思路很硬。
  - “编程”对象正在变化。
    以前我们编程的是函数和服务；现在开始编程的是实验室、团队、工作流、评审机制。
    program.md 这种东西，本质上是在“编排一个研究组织”。
  - 很多领域的瓶颈，可能不再是模型智力，而是接口设计。
    谁先把一个领域变成“可运行、可评估、可积累”的模板，谁就先把这个领域交给 agent 了。

  但它也给一个很清醒的提醒：

  - 不是所有事情都适合这样做。
    只有当问题能被结构化、能自动执行、能稳定评估时，这套方法才真正有效。
    否则 agent 只会高频地产生噪音。

  如果把这些启发压成一句话，就是：

  智能体时代最重要的不是“让 AI 替你思考”，而是“把问题改造成 AI 能持续试错并产生复利的系统”。

  如果你愿意，我可以继续往下讲一层：
  为什么这件事对产品设计、创业、组织管理的启发，甚至比对科研本身更大。
• 更大的启发
  之所以说这件事对产品、创业、组织的启发更大，是因为科研只是最先被看清的一种“搜索问题”。

  科研可以写成：

  假设 -> 实验 -> 指标 -> 保留/丢弃

  而很多现实工作其实也一样：

  - 产品：用户假设 -> 功能改动 -> 上线 -> 行为数据 -> 保留/回滚
  - 创业：市场假设 -> 方案/定价/渠道 -> 转化与留存 -> 继续/放弃
  - 组织：流程假设 -> 分工/机制 -> 执行质量 -> 调整制度

  一旦你这样看，重点就变了：
  不是“做一个聪明的 agent”，而是“把业务改造成可搜索、可评估、可积累的系统”。

  对产品的启发
  最重要的变化是：产品团队以后真正要设计的，可能不是单个功能，而是功能实验系统。

  好的产品组织，会越来越像这样：

  - 明确哪些参数可以快速试
  - 明确什么是成功指标
  - 明确回滚条件
  - 让 agent 持续提出小改动并验证

  所以未来产品经理最值钱的能力，不只是“想功能”，而是：

  - 把模糊需求压成可测试假设
  - 把目标压成可观测指标
  - 把上线流程压成低成本试错闭环

  对创业的启发
  创业过去常被理解为“找到一个天才点子”，但这个思路告诉你，真正稀缺的可能是持续发现有效点子的机器。

  也就是：

  - 不靠一次大判断
  - 靠快速生成假设
  - 快速测试渠道、定价、定位、功能
  - 让有效尝试沉淀成新基线

  所以创业公司未来的核心竞争力，可能越来越像：

  - 更快的实验速度
  - 更低的试错成本
  - 更清晰的 evaluator
  - 更强的知识沉淀能力

  不是“我们比别人更聪明”，而是“我们比别人更会形成复利”。

  对组织的启发
  这对组织管理的启发尤其大。

  - 决策中心
  - 审批中心
  - 信息瓶颈

  但按这个思路，优秀管理者更像：

  - 协议设计者
  - 边界定义者
  - 评价函数设计者
  - 知识沉淀机制维护者

  也就是说，管理的本质从“替大家做判断”，变成：

  - 定义哪些事可以自主试
  - 定义什么叫试得对
  - 定义什么时候必须人工介入
  - 定义如何把失败变成组织记忆

  这其实比“自动科研”更深，因为它在重新定义公司。

  最硬的一条启发
  未来很多团队的上限，不取决于单个成员有多强，而取决于：

  这个团队有没有一个能让人和 agent 持续试错、持续积累、持续改进的操作系统。

  没有这个系统，再强的人也只能靠英雄主义。
  有了这个系统，普通能力也能复利。

  但也有一个风险
  这套思想很强，也很危险。最大的坑是：

  一旦 evaluator 设计错了，整个系统会高速朝错误方向优化。

  科研里会变成刷指标。
  产品里会变成刷点击。
  创业里会变成刷短期收入。
  组织里会变成刷汇报好看。

  所以真正高水平的工作，不只是搭闭环，而是设计对的闭环。

  如果你愿意，我下一步可以继续讲最实际的一层：
  一个普通团队，怎么把自己的工作流改造成“agent 可参与的闭环系统”。


› 好的


• 一个普通团队，最应该做的不是“上 AI”，而是先把工作拆成可循环优化的单元。

  最小做法

  - 先选一条流程，满足 4 个条件：高频、低风险、反馈快、结果可量化。
  - 把这条流程写成固定接口：输入是什么，agent 能改什么，怎么执行一次，输出什么结果。
  - 定一个 evaluator：什么叫更好，什么叫更差，什么情况必须人工否决。
  - 每次尝试都记录：改了什么、结果如何、保留还是丢弃。
  - 只在这条流程跑通后，再扩到第二条，不要一开始做“全公司自治”。

  一个通用骨架
  你可以把任何流程先压成这个结构：

  task -> proposal -> change -> run -> evaluate -> keep/discard -> log

  落到文件上，最小可以长这样：

  workflow/
    editable/        # agent 允许修改的内容
    run.sh           # 执行一次流程
    evaluate.py      # 输出结构化指标
    results.json     # 本次结果
    history.tsv      # 所有尝试记录

  普通团队最适合先改造的场景

  - 产品团队：落地页文案、定价页文案、引导流程、小实验 A/B。
  - 研发团队： flaky test 修复、CI 失败归因、性能回归定位、代码迁移。
  - 运营团队：客服回复草稿、FAQ 更新、标题优化、渠道投放素材筛选。
  - 数据团队：报表异常归因、特征试验、规则调参、告警降噪。

  这些事的共同点是：反馈周期短，成败能看出来。

  别先碰的东西

  - 公司战略
  - 品牌主叙事
  - 长周期、低样本决策
  - 没有稳定 evaluator 的创意工作
  - 错一次代价很高的核心流程

  这些地方先让 agent 做“辅助”，不要做“自治”。

  推荐的 3 个阶段

  - 阶段 1：Copilot
    agent 只提建议，人执行、人判断。
  - 阶段 2：Operator
    agent 能执行，但必须人工审批 keep/discard。
  - 阶段 3：Loop
    agent 在明确预算和边界内自动循环，人工只看日报和异常。

  大多数团队先做到阶段 2 就已经很有价值。

  最关键的一点
  不要先追求“更聪明的 agent”，先追求：

  - 更清晰的任务边界
  - 更稳定的执行脚本
  - 更可靠的评价函数
  - 更完整的实验日志

  系统设计对了，agent 才有复利；系统设计错了，只会更快地产生垃圾。

› 产品团队


• 如果是产品团队，最值得借这套思想的，不是“让 agent 写 PRD”，而是：

  把产品工作改造成可持续实验的闭环。

  产品团队最适合先做的，不是大版本规划，而是这三类事：

  - 漏斗优化：注册、激活、下单、付费、续费
  - 文案与呈现优化：landing page、paywall、引导页、按钮文案
  - 触达策略优化：push、邮件、站内提醒、召回

  这些问题天然适合写成：

  假设 -> 改动 -> 上线/模拟 -> 数据 -> keep/discard

  最小落地方式
  先选一条具体漏斗，比如“新用户注册到激活”。

  把它定义成一个模板：

  product_loop/
    goal.md               # 目标、边界、成功标准
    baseline.json         # 当前漏斗数据
    editable_surfaces.md  # agent 能改哪些东西
    ideas.json            # 历史实验想法
    runbook.md            # 怎么发起实验
    evaluator.py          # 读取实验数据并输出结论
    history.tsv           # 每次实验记录

  goal.md 里只写 4 件事：

  - 目标指标：如 activation_rate
  - 护栏指标：如投诉率、退款率、次日留存
  - 可改范围：文案、排序、默认选项、页面结构中的某些模块
  - 禁区：价格体系、核心结算逻辑、合规文案

  agent 在产品团队里该干什么
  它最适合承担的是：

  - 读历史实验和当前漏斗
  - 提出 3 到 5 个可执行假设
  - 把假设改写成实验方案
  - 生成文案/UI 变体/实验配置
  - 实验后读数据，写 keep/discard 建议
  - 把经验沉淀进实验库

  它不该直接决定：

  - 产品方向
  - 品牌主叙事
  - 重大策略取舍
  - 没有护栏的全量发布

  产品团队的闭环应该怎么设计
  我建议是这个顺序：

  1. 先定义 evaluator
     不是先问 agent 能做什么，而是先定义：

  - 什么叫赢
  - 多久看一次
  - 到什么幅度才算有效
  - 哪些指标一坏就立刻回滚

  2. 再定义可改界面
     把产品里能安全试错的部分列出来，比如：

  - 标题、副标题、CTA
  - 默认选项
  - onboarding 步骤顺序
  - 推荐卡片排序规则
  - push 触发时机
  - 邮件标题和首段

  3. 再让 agent 提案
     格式固定，例如：

  {
    "name": "shorter_signup_copy",
    "hypothesis": "减少注册页认知负担会提升完成率",
    "change": "将主标题缩短，副标题改为结果导向表达",
    "primary_metric": "signup_completion_rate",
    "guardrails": ["bounce_rate", "support_ticket_rate"],
    "risk": "表达过度承诺"
  }

  4. 执行并记录
     每次实验必须有统一记录：

  - 改了什么
  - 对谁生效
  - 跑了多久
  - 指标变化
  - keep/discard
  - 复盘一句话

  最推荐的试点场景
  如果你是一个普通产品团队，我建议第一个试点只做这类问题：

  - 注册页文案与结构优化
  - onboarding 第一步引导优化
  - paywall 标题/套餐默认项优化
  - push/邮件召回文案优化

  原因很简单：

  - 反馈快
  - 风险低
  - 易回滚
  - 数据清楚

  不要一开始就做的事

  - 让 agent 自动写完整 PRD
  - 让 agent 直接改核心产品逻辑
  - 让 agent 同时改文案、流程、定价三件事
  - 只看点击率，不看后续留存/退款/投诉
  - 没有实验日志和回滚机制

  产品团队里人的角色会怎么变
  这套方法下：

  - PM 不再主要写 PRD，而是定义目标函数和试验边界
  - 设计师 不再只是出稿，而是定义可组合的界面实验面
  - 工程师 不再只接需求，而是建设实验基础设施和安全开关
  - 数据分析师 不再只是报数，而是定义 evaluator 和因果判断规则

  也就是说，团队从“做功能”转向“运营实验系统”。

  一句最实用的建议
  如果你想真开始，不要问：

  “我们怎么用 agent 做产品？”

  而要问：

  “我们产品里哪一段流程，已经足够标准化，能让 agent 连续跑 20 次小实验？”

  先找到那一段，再搭最小闭环。
