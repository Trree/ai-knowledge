# 窄场景 Topic Wiki 首包需求文档

状态：Draft v0.1
来源：`2026-04-22-karpathy-llm-wiki.md`
类型：服务型 MVP PRD

## 1. 文档目的

本文将原始策略分析整理为一份可评审、可执行、可验收的需求文档。

其中标注为 `工程化补充` 的内容，不是原文逐句结论，而是为了让 MVP 能真正落地所补齐的产品要求。

## 2. 产品定义

`窄场景 Topic Wiki 首包` 是一个固定边界的服务产品，面向已经收集了大量主题资料、但无法把这些资料变成可持续复用知识资产的用户。

该服务交付一个单主题 wiki，它必须同时满足以下条件：

- 可持续提问
- 可追溯来源
- 有明确 schema
- 可在交付后继续增长

这个产品不是通用 SaaS，不是课程，也不是企业知识库整体迁移服务。

## 3. 背景与问题

原始文档判断：`LLM Wiki` 的热度已经足够高，用户也开始理解“知识库可以由 LLM 持续维护”这件事，但大多数用户仍然无法完成第一步落地，也不会因为抽象教程就开始自己搭建。

目标问题是：

`我有很多资料，但这些资料并没有变成一个我可以持续提问、持续复用、持续扩展的知识资产。`

原始文档同时指出一个核心风险：

`用户会觉得这个概念很酷，但最后仍然不会在日常中使用。`

因此，MVP 必须优先卖“看得见的结果”，而不是卖“平台愿景”。

## 4. 产品目标

在明确边界内，把用户分散的主题资料编译成一个可用、可追溯、可继续扩展的 Topic Wiki，并验证用户是否愿意为这种结果付费。

## 5. 目标用户

核心用户：

- 研究型创作者
- 独立研究者
- AI 从业者里重度使用 agent、积累了大量链接、论文、笔记、会议纪要和对比资料的人

明确不服务的人群：

- 想做企业全量知识库迁移的团队
- 只想学方法、不想买结果的人
- 主题边界不清、资料范围无限扩张的人

## 6. 核心价值主张

把用户过去 3 个月收藏但没真正用起来的资料，在 7 天内编成一个可持续追问的 Topic Wiki。

交付物不是：

- 聊天记录
- 一个 RAG demo
- 一个泛泛而谈的 second brain 概念

交付物是：

- 一个单主题 wiki
- 一套该主题的 schema
- 一套可继续 ingest、query、lint 的使用方式
- 一个带 source trace 的初始知识结构

## 7. 产品形态与定价

产品形态：服务

MVP 商业要求：

- 首批内测价：`999 RMB`
- 固定边界交付
- 只有在主题和资料范围确认后才开始生产

## 8. 范围定义

### 8.1 范围内

- 只做 `1` 个主题
- 最多接收 `30` 份 source
- 交付 `1` 套 Obsidian/Codex 可用的 wiki 包
- 只做 `1` 次初始 ingest
- 包含 `1` 次 handoff
- 包含 `1` 份 lint/风险说明

### 8.2 范围外

- 企业全库迁移
- 一个订单里做多个主题
- 把插件作为独立第一产品出售
- 直接做通用 SaaS 平台
- 长期代运营或持续托管更新

## 9. 交付物

原始文档要求把 demo 和正式交付都拆成 6 个可见件。因此 MVP 的交付包必须包含：

1. `raw/`
2. `wiki/`
3. `schema/`
4. `index/`
5. `query-demo/`
6. `lint-report/`

`工程化补充`

建议最终目录结构如下：

```text
topic-wiki-package/
  raw/
  wiki/
  schema/
  index/
  query-demo/
  lint-report/
  README.md
```

## 10. 用户流程

### 10.1 购买流程

1. 用户先看到一个公开 before/after demo。
2. 用户提交一个主题和一组资料。
3. 交付方确认是否符合首包边界。
4. 用户支付内测价或定金。
5. 交付方完成资料编译与组织。
6. 用户收到交付包和 handoff。
7. 用户验证这个 wiki 是否真的能回答问题、是否值得继续维护。

### 10.2 交付流程

1. intake 与范围确认
2. source 收集与规范化
3. schema 设计
4. wiki 编译
5. query 演示
6. lint 与风险检查
7. handoff

## 11. 功能需求

### FR-01 主题 intake

系统或交付流程必须收集以下信息：

- 主题名称
- 用户希望解决的核心问题
- source 列表
- source 类型
- 预期使用场景

验收标准：

- 如果用户不能明确说出单一主题，订单不能进入生产
- 如果资料覆盖多个不相关主题，必须先缩边界再继续

### FR-02 资料边界控制

首包必须强制执行边界：

- 最多 `30` 份资料
- 仅 `1` 个主题
- 不接企业全库迁移

验收标准：

- 超范围需求必须在生产开始前被缩减或拒绝

### FR-03 初始 ingest

首包必须完成一次初始 ingest，把批准范围内的资料转换成可组织、可索引的主题语料。

验收标准：

- 所有批准的 source 都进入 `raw/`
- 所有 source 都在 `index/` 中可见

### FR-04 schema 定义

首包必须为该主题定义一套清晰 schema，用来约束 wiki 的结构和页面组织方式。

验收标准：

- `schema/` 中明确描述该主题的主要页面类型或实体类型
- `wiki/` 中的页面遵循这套 schema，而不是随意堆砌

### FR-05 wiki 编译

首包必须产出一个单主题 wiki，而不是一个资料堆。

验收标准：

- `wiki/` 目录结构清晰
- 用户能够把它当作“可继续增长的知识资产”使用，而不只是一次性整理结果

### FR-06 source trace

首包必须保留 source trace，让用户能从 wiki 回看原始资料。

验收标准：

- 关键结论、摘要或页面可以追溯到原始 source
- 交付包中能看见 `raw/` 与 `wiki/` 之间的对应关系

### FR-07 query 演示

首包必须提供一份 query 演示，至少回答以下 3 个问题：

1. `我们知道什么？`
2. `哪些地方互相矛盾？`
3. `接下来该补什么资料？`

验收标准：

- `query-demo/` 中必须包含对这 3 个问题的具体回答

### FR-08 lint 与风险报告

首包必须提供一份 lint/风险报告。

报告至少覆盖：

- 资料覆盖不足的区域
- 明显冲突点
- 可能的 drift 风险
- 后续建议补充的资料方向

验收标准：

- `lint-report/` 必须存在
- 报告里至少有一条明确、可执行的下一步建议

### FR-09 handoff

首包必须包含一次 handoff，告诉用户后续如何继续 ingest、query、lint。

验收标准：

- 交付包中存在 README 或等价说明
- 用户在没有二次讲解的前提下，也能理解后续如何继续使用

## 12. 非功能需求

### NFR-01 清晰性

交付结构必须足够清晰，让第一次接触该包的用户能快速理解每个目录的用途。

### NFR-02 可控交付

首包必须保持在单人可交付的边界内。

`工程化补充`

建议 beta 交付 SLA：资料冻结后 `7` 个自然日内交付。

### NFR-03 可增长性

交付物必须能继续增长，不能只是一次性的演示材料。

### NFR-04 信任感

交付物必须足够透明，能降低用户对幻觉、drift 和黑盒总结的担忧。

## 13. 验收标准

只有同时满足以下条件，首包才算交付完成：

1. 总资料数不超过 `30`，且主题只有 `1` 个。
2. 交付包包含 `raw/`、`wiki/`、`schema/`、`index/`、`query-demo/`、`lint-report/`。
3. wiki 的结构清晰，并遵循一致 schema。
4. 用户可以从关键输出追溯回 source。
5. query demo 能回答 3 个指定问题。
6. lint 报告能指出冲突、缺口或后续补料方向。
7. 用户收到可执行的 handoff 说明。

## 14. 成功指标

原始文档给出的 MVP 验证信号是：

- `72` 小时内拿到至少 `3` 个明确咨询
- 或拿到至少 `1` 个付费定金
- 或拿到至少 `5` 个愿意提供真实资料试做的用户

补充运营指标：

- 用户愿意提供真实资料，而不是只夸概念
- 用户愿意用自己的主题复刻同样交付
- 用户在首包之后对模板或 Starter Kit 产生兴趣

## 15. 失败信号

以下情况出现时，说明需求尚未被验证：

- 用户只觉得概念酷，但不愿意交真实资料
- 用户只想要教程，不想买结果
- 用户看不见“一次整理之后还能继续用”的价值
- 范围总是不可控地扩张，导致首包无法标准化

## 16. 上线与销售要求

最短成交路径应为：

1. 先做一个公开 demo
2. 再做一页试卖文案
3. 再做限量内测
4. 首批交付结束后，再把模板抽出来卖给第二批用户

销售表达要求：

不要卖 `second brain`。

要卖：

`把你的散资料编成一个可持续提问的 Topic Wiki。`

## 17. 非目标

这个 MVP 不试图证明以下能力：

- 大规模团队级检索架构
- 图结构或 deterministic retrieval 的规模化能力
- 无人监督的长期自动维护
- 企业治理平台能力

这些能力可以是后续阶段的演化方向，但不是首包必须证明的内容。

## 18. 关键风险与应对

风险：用户觉得概念有趣，但不会持续使用

应对：

- query demo 必须回答真实工作问题，而不是只给抽象总结

风险：用户不信任 wiki 的综合结果

应对：

- 强制保留 raw 对照和 source trace

风险：交付边界失控，导致单位经济模型失效

应对：

- 在开工前就强制执行首包边界

风险：过早进入通用 SaaS 红海

应对：

- 先保持为服务产品，延后平台化

## 19. 待验证问题

下一轮必须继续验证的问题：

1. 用户买单更强的动机，到底是“第一次把资料整理成能工作的东西”，还是“获得一个长期可持续的知识资产”？
2. 哪类人群转化更快：研究型创作者，还是小团队 owner？
3. 哪种销售文案转化更高：`把散资料变成可提问资产`，还是 `帮你搭一个 Karpathy 风格的 LLM Wiki`？
4. 首包交付后，2 到 4 周内有多少用户还会继续使用这个 wiki？

## 20. 下一步

当前最优先动作：

- 产出 1 个公开 demo
- 写 1 页销售文案
- 招募首批限量内测用户
- 在真实付费出现前，不扩展为更大的平台产品
