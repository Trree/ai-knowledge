# Claude Code 的自我迭代，真正值得我们学的不是工具，而是一套工程飞轮

最近看了一篇关于 Claude Code 团队如何做自我迭代的文章，里面有一个很有意思的事实。

Claude Code 的代码里，相当大一部分是用 Claude Code 自己写出来的。

这句话听起来有点像营销，但它真正重要的地方不在于「AI 写了多少代码」，而在于这背后形成了一套很完整的工作方式：

自己用工具开发自己，发现问题，快速做成新功能，再继续用新功能改进自己。

这就是一个工程飞轮。

## 一、需求不是拍脑袋来的，是从真实使用里长出来的

Claude Code 团队最特别的地方，是他们每天都在用自己的产品工作。

这不是普通意义上的 dogfooding，而是更深一层的内部使用。工程师、数据科学家、安全团队、基础设施团队都在真实项目里用 Claude Code。团队可以直接看到大家怎么用、哪里卡住、哪些地方被反复绕过。

更有意思的是，他们特别关注一种信号，叫「用户滥用」。

也就是用户拿产品去做设计者原本没想到的事。

普通团队看到这种行为，可能会觉得用户用错了。Claude Code 团队反而会问，为什么大家会这么用？这里是不是藏着一个真实需求？

很多好功能不是从会议室里想出来的，而是从用户的奇怪用法里长出来的。

这对我们很有启发。

不要只问用户想要什么，也要观察用户已经在勉强用什么、绕路用什么、重复做什么。

## 二、PRD 不是没用，但原型更接近真实答案

文章里提到一个很关键的判断，Claude Code 这种产品很难从静态 PRD 或 Figma mockup 开始。

因为 AI agent 的能力边界不是靠想象判断的。

你必须让它真的跑起来，真的读文件、改代码、跑测试、失败、修复，再看它到底能做到哪一步。

所以他们更倾向于用原型替代漫长的文档讨论。一个新功能可能会做十几个可运行原型，而不是先写一份很长的需求文档。

这不是说不要思考，而是把思考变成可运行的东西。

对我们来说，可以学的不是「取消 PRD」，而是减少纯口头争论。

遇到不确定的问题，先做一个最小可用原型。原型跑起来以后，很多争论会自然消失。

## 三、任务分解的关键，是先让 AI 计划，再让 AI 执行

Claude Code 的一个典型工作流是：

先进入 Plan Mode，让 Claude 反复梳理方案，直到计划足够清楚。

然后再切到执行模式，让它开始改代码、跑测试、修复问题。

这件事很重要。

很多人用 AI 写代码失败，不是因为 AI 不会写，而是因为一上来就让它动手。结果它理解错目标，顺手改了很多不该改的地方，最后人还得收拾残局。

正确方式应该是先把「要做什么、为什么这么做、边界在哪里、如何验证」说清楚。

复杂一点的任务，还可以让 Claude 先反过来采访你，问清楚技术实现、用户体验、边界情况、取舍点，然后生成一份 spec，再新开一个干净 session 执行。

这其实很像传统工程里的需求澄清，只是速度快了很多。

## 四、上下文管理，是 AI 工程化的地基

文章里反复提到 CLAUDE.md、Session Memory、rules、subagents 这些东西。

它们本质上都在解决同一个问题：

不要让每次 AI 工作都从零开始。

CLAUDE.md 存的是项目长期规则，比如架构约定、代码风格、常见错误、测试命令。Session Memory 存的是跨会话的工作记忆。rules 可以记录某些路径或模块的特殊规则。subagents 则把复杂任务拆成独立上下文，避免主会话被大量日志和搜索结果污染。

这背后的判断很朴素。

如果一个规则你已经跟 AI 说过两次，就不应该第三次还靠嘴说。

应该把它写进仓库、规则文件、测试、hook 或 CI 里。

## 五、质量不是靠信任 AI，而是靠验证闭环

Claude Code 团队并不是「相信 AI 写的代码一定对」。

相反，他们非常重视验证。

比如 TDD，先写测试，确认测试失败，再让 Claude 实现直到测试通过。这样可以防止 Claude 为了通过测试去偷偷改测试。

比如 hooks，在工具调用后自动跑格式化、lint、测试。

比如多 agent code review，让不同 agent 分别检查风格、历史上下文、明显 bug，再用另一批 agent 过滤误报。

这里有一个很值得记住的原则：

AI 可以加速生成，但不能替代验证。

如果没有测试、截图、日志、预期输出，AI 很容易给出「看起来完成了」的结果。真正可靠的工作流，一定要把验证方式前置。

## 六、发布和事故处理，也被纳入 AI 工作流

文章里还有一个点容易被忽略。

Claude Code 团队不是只在写代码阶段用 AI，而是把 AI 放进完整工程流程里。

发布上，用 feature flag、内部 dogfood、灰度、快速回滚来控制风险。

事故处理上，把 stack trace、日志、相关文档交给 Claude，让它帮忙沿着控制流定位问题、整理 runbook、生成复盘材料。

知识沉淀上，每次发现重复错误，就回写 CLAUDE.md、REVIEW.md、runbook、测试或 CI。

也就是说，AI 不是一个孤立的聊天窗口，而是接进了需求、实现、审查、发布、事故、复盘和知识库的整个链路。

这才是它真正变强的原因。

## 七、我们可以怎么迁移这套方法

如果公司内部要借鉴这套实践，我觉得可以先从五件小事开始。

第一，给每个重要仓库补一份 AI 可读的项目说明，比如 CLAUDE.md，写清楚项目结构、常用命令、代码风格和常见坑。

第二，复杂任务先写 spec，再执行。不要一上来就让 AI 改代码。

第三，把验证前置。能写测试就先写测试，不能写测试也要有明确的验收命令、截图或检查清单。

第四，把重复提示沉淀下来。说过两次的规则，就不要再靠口头记忆。

第五，用 AI 做 code review，但不要让它替代 CI 和人工判断。AI 更适合帮我们扩大检查面，不适合独自承担最终责任。

## 最后

Claude Code 团队真正厉害的地方，不是「他们用了 Claude Code」。

而是他们把 Claude Code 变成了一套可以自我强化的工程系统。

需求来自真实使用，想法用原型验证，任务先计划再执行，质量靠测试和审查兜底，经验沉淀回仓库，沉淀后的规则又让下一次 AI 工作更靠谱。

这就是飞轮。

我们不一定要照搬他们的工具，但非常值得照搬这个思路：

不要只把 AI 当成一个更快的程序员。

要把 AI 接进团队的工作流里，让它参与发现、实现、验证、复盘和沉淀。这样它带来的就不只是效率提升，而是整个团队工程能力的升级。
