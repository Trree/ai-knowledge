## 发生了什么

这个项目 UI 改了很多遍，每次都达不到想要的效果：
- 改颜色 → 不满意 → 再改
- 改布局 → 不满意 → 换方案

- 每次改动都是表层修补，没有向前推进

---

## 根本原因

### 1. 把"感觉不对"当成了输入，而不是症状

每次觉得某个颜色/布局不对，直接去改颜色/布局。
这个时序是错的——"感觉不对"是一个信号，告诉你**上游有个问题没回答**，而不是"执行层需要调整"。

### 2. 从没回答过最上游的问题

> 用户打开这个 dashboard，3 秒内应该知道什么？

这个问题从没被精确回答过。
没有这个锚点，"好看"和"准确"都是在没有坐标系的空间里做选择——所以永远摇摆。

### 3. 用执行来逃避上游的不舒服

"我到底想要什么效果"比"这个颜色对不对"更难回答，也更令人焦虑。
大脑自动跳到执行层，因为改颜色有立刻反馈。
但真正的问题被回避了，所以每次改完都不满意，进入死循环。

### 4. 范围估计不足（技术层面）

本次重设计计划只列了 6 个 CSS 文件，实际需要改 15+ 个文件。
因为没有先扫描全量，导致实施中途才发现遗漏。

---

## 解决方案

### 思维层面（防止再次陷入循环）

**每次想动手改 UI 之前，先写完这一句话：**

> "用户打开这个页面，3 秒内应该知道 ___。"

两种结果：
- 30 秒内写完 → 可以动手
- 写不出来，或写了好几个版本 → 这就是模糊的位置，在这里停下来，不要动手

**识别逃跑动作：**
当你有冲动去改某个颜色/间距/布局时，先问自己：
> "我在改这个，是因为它违反了某个已经想清楚的上游决定，还是在用这次改动来回避那个上游问题？"

大多数时候是后者。

**耐受上游不确定性：**
写不出那句话的时候，就坐在那个不舒服里，直到写出来。
不要用执行层的活动来填补思考层的空缺。

### 技术层面（防止范围遗漏）

改 CSS token 体系之前，先扫描全量文件：
```bash

```
