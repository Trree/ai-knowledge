# Claude Code 装了一堆 Skill 之后，变慢的不是网络——是你从没打开过的那 70%

上周我打开 Claude Code，随手问了个简单问题。响应比平时慢了一拍。

不是网络的问题。是 system prompt 里塞了 47 个 Skill 的描述——每次对话，模型都要先"通读"这 47 段说明书，然后才开始想我的问题。

我想知道到底有几个在用。跑了一次数据，结果很扎心：**七成从未被调用。**

## 你也有这种抽屉

打开 Skill 目录，47 个文件夹码得整整齐齐。试着回忆每个的用途——到第 15 个就放弃了。

有些是半年前看别人推荐随手装的，有些是为了某个项目临时装的，还有两个图片生成 Skill，至今分不清该用哪个。

就像手机里 200 个 App，真正每周打开的不超过 20 个。但你不删，因为——**"万一以后用到呢？"**

这句话是所有膨胀的起点。

## 膨胀的代价比你以为的大

表面上看，多装几个 Skill 无非是列表长一点。但实际有两层隐性成本：

**第一层伤害在你身上。** 每次想用 Skill，你得在一堆名字里做选择。两个功能相似的 Skill 摆在面前，你要花 10 秒想"用 A 还是用 B"。这种微小的决策摩擦日积月累，消耗的是你真正用来思考问题的精力。

**第二层伤害在模型身上。** Claude Code 会把所有 Skill 描述塞进 system prompt。47 个 Skill 意味着大量的上下文篇幅，模型的注意力被稀释。你给它的问题，它得在一堆无关的 Skill 描述中"找路"。你为不用的 Skill 支付了隐形的智力税。

Skill 膨胀不是"列表太长看着烦"的审美问题，是实打实影响效率的工程问题。

## 为什么膨胀会持续恶化

想管理，先得有数据。但问题就在这里——**你根本不知道自己在用哪些 Skill。**

我问自己：过去一个月，用过哪些 Skill？频率是多少？答不上来。凭印象猜，大概有十几个"经常在用"。但"印象"这东西，往往和现实差距巨大。

没有度量，所有管理决策都是凭感觉。而凭感觉的结果永远是"先留着吧"。

## 转机：一个被低估的能力

Claude Code 有一个叫 **Hook** 的机制——在特定事件发生时，自动执行你指定的脚本。

比如你可以配一条规则：**每当任何 Skill 被调用，自动记一笔。**

在 `~/.claude/settings.json` 中追加：

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Skill",
        "hooks": [
          {
            "type": "command",
            "command": "bash ~/.claude/hooks/skill-tracker.sh",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

就像给抽屉装了一个计数器——每拿出一样东西，自动划一道正字。你不需要改变任何使用习惯，照常用就行，数据在后台默默积累。

跑两周，运行一次审查脚本，你会看到这样一份报告：

```
使用频次排行:
  32  commit
  18  translate
  14  ljg-card
   3  review-pr
   1  skill-recommender

零调用 Skill（安装了但从未使用）:
   ✗ baoyu-comic
   ✗ baoyu-slide-deck
   ✗ ljg-relationship
   ... 还有 26 个

已安装: 47 | 活跃: 11 | 零调用: 33
膨胀率: 70%
```

我第一次看到这份报告的时候，沉默了很久。

47 个 Skill，只用了 11 个。超过三分之二是"沉默的乘客"——占着 system prompt 的位置，消耗模型的注意力，从未被调用。

更扎心的是使用模式。我以为自己需要某个 Skill 的"全部功能"，数据告诉我——我只用了它一种参数。**你以为自己需要的，和实际使用的，是两个东西。**

## 有了数据，然后呢？

看到报告，自然会想：能不能自动把不用的 Skill 删掉？

我一开始也这么想。但很快意识到这个思路有问题——**万一某个 Skill 只是最近没用，下个月的项目恰好要用呢？**

自动删除太危险。但永远不删也不行。

正确的方案不是"自动化决策"，而是**自动化提醒**。

每隔两周，Claude Code 启动时检查上次审查的日期。超期了，弹一句温柔的提醒——

> 距上次 Skill 盘点已过 18 天。已安装 47 个，近两周活跃 9 个。要花两分钟看看吗？

不自动删除任何东西。只是在你即将遗忘的时候，把你拉回"整理的现场"。

**自动化的最高境界不是替你做事，是在正确的时刻推你一把。**

## 整理不是一次性事件

你可能会想：花半小时一次性把不用的 Skill 全清掉不就行了？何必搞什么自动追踪？

我试过。清完之后很清爽，持续了大概两个月。然后不知不觉又装了十几个新 Skill，回到原点。

**整理不是一次性事件，是一个需要维持的习惯。**

这和健身一样——你不会因为去了一次健身房就永远保持身材。你需要一个持续可见的反馈回路：记录→审查→决策→记录→审查→决策……

数据采集提供"记录"，审查报告提供"审查时刻"，定期提醒保证你不会无限期拖延。而最终的"删还是留"，永远由你来决定。

## 一个意外的发现：约束是好事

折腾 Hook 的过程中，我遇到了不少限制。脚本必须 10 秒内跑完，超时直接被杀；Hook 只能在 Skill 执行后记录，不能阻止调用。

一开始觉得这些是缺陷。后来发现恰恰相反——**这些约束逼出了更好的设计。**

因为只有 10 秒，采集脚本必须极简，只记录不分析。因为无法阻止执行，必须先积累数据，而不是上来就写拦截规则。因为 payload 里没有时间戳，脚本必须自给自足。

如果 Hook 什么都能做，我可能会写一个 500 行的"智能管家"脚本，然后在某天凌晨它把我正在用的 Skill 给删了。

**约束不是自由的对立面，约束是秩序的来源。**

## 四个道理

**一、先有数据，再谈管理。** 没跑审查报告之前，我以为自己"大部分 Skill 都在用"。数据说只有 24%。人对自己行为的感知，往往不靠谱。

**二、自动化的边界要画清楚。** 采集和提醒可以自动化。但"删还是留"的判断不能。只有你自己知道，一个 Skill 是"真的不需要了"还是"暂时没有场景"。

**三、管理工具不能比问题更复杂。** 全部方案就是几个小脚本。如果为了管理 Skill 膨胀，搭一个带数据库、带 Web 界面的管理平台——管理工具本身就成了新的膨胀。

**四、80% 的收益来自最简单的那一步。** 光是"知道自己在用什么"——不需要任何自动化清理、不需要任何智能推荐——就已经解决了大部分问题。因为看到 70% 的膨胀率之后，你会自己动手删的。

## 还没解决的问题

坦诚说，有两件事暂时做不到：

**语义重叠检测。** 我有两个图片生成 Skill，数据显示两个都在用，但功能几乎一样。调用频次无法发现这种重叠——只有真正理解 Skill 的功能描述，才能判断"这两个是不是重复了"。也许未来可以用 LLM 来做。

**动态加载。** 最理想的状态是根据历史数据，只把常用 Skill 放进 system prompt，其余按需加载。既不用删除，又不污染上下文。但这需要官方支持，单靠 Hook 做不到。

不过这些都是锦上添花。核心问题——**不知道自己在用什么**——已经解决了。

---

如果你也被 Skill 列表的长度压得有点喘不过气，试试最简单的一步：

给 Hook 装一个采集脚本，不改变任何使用习惯，让它默默记录两周。然后运行一次审查。

你可能会像我一样，对着那个膨胀率沉默很久，然后默默开始删东西。
