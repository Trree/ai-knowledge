
> 方法：只使用当前项目根目录的 `goal-driven-agent` skill。  
> 研究时间：2026-04-20

## 一句话结论

程序员未来的工作流程，不会是“AI 替代程序员”，而会更像：**人负责目标、约束、架构、验收与取舍，agent 负责搜索、起草、改写、测试、修复、提交和并行执行。**  
更具体地说，未来的主流程会变成两条并存的 loop：

- `同步 loop`：人和本地 agent 在 IDE / 终端里一起做高歧义、高风险、需要即时判断的工作。
- `异步 loop`：人把定义清楚的任务扔进 issue / task queue / PR 流里，让云端 agent 在后台完成并回传结果。

程序员会从“主要亲手写代码的人”，逐步变成“管理问题定义、上下文、验证闭环和多 agent 协作的人”。

## 现象

过去一年里，主流 coding 产品已经不再只是补全代码，而是在向完整工作流渗透。

- OpenAI 的 Codex 从“在云端软件工程环境中并行执行任务”走向更广泛的软件开发工作流，说明 AI 不再只是 IDE 里的局部自动补全，而是在吃掉真正的任务单元。
- GitHub Copilot 的 coding agent 已经直接接入 issue、pull request 和 GitHub Actions，说明 AI 正在进入团队协作和交付链路。
- Anthropic 的 Claude Code 把终端、仓库、测试、工具调用放进统一回路，说明未来主战场不只是编辑器，而是整个工程环境。
- Google 的 Jules 强调把 bug fix、版本升级、文档更新这类任务异步委托给 agent，说明“后台并行做事”会成为默认模式。

如果只看效率证据，结论也不是单向度的：

- GitHub 在 2022 年公布的受控实验里，使用 Copilot 的开发者完成指定任务快了 55%。
- 但 METR 在 2025 年 7 月针对资深开源开发者、在自己熟悉仓库上的随机对照研究里，观察到早期 2025 的 AI 工具让任务平均慢了 19%。
- METR 在 2026 年 2 月又更新说，随着 agent 工具普及，后续实验很可能低估了真实提速，因为很多开发者已经不愿在无 AI 条件下工作，而且会主动把“高 AI 收益”的任务筛出去。

这些信号指向同一个变化：程序员的基本工作单位，正在从“写一段代码”变成“定义一个任务，并让人和 agent 一起把它做完”。

更重要的是，产品形态已经开始分化成两类：

- 本地同步型：程序员在终端或 IDE 里边想边做，适合调试、探索、重构、设计讨论。
- 云端异步型：程序员把任务交给后台 agent，在 branch / PR / issue 上等待结果，适合脚手架、测试、修小 bug、补文档、升级依赖。

未来工作流不会只剩一种，而是这两种并存，然后由人决定什么该同步做，什么该异步委托。

## 未来工作流

### 1. 定义问题，而不是直接开始写

未来的第一步不再是打开编辑器，而是先把任务定义清楚：

- 目标是什么
- 成功标准是什么
- 不允许破坏什么
- 代码、文档、测试、权限、依赖的边界在哪里

这一步会越来越像给 agent 写任务合同，而不是给自己写待办。  
从 OpenAI 对 Codex 的内部最佳实践看，大任务往往先进入 `Ask / 计划`，再进入 `Code / 执行`；而且 prompt 最好写得像 GitHub issue，带上文件路径、模块名、约束和参考实现。

### 2. 准备上下文，而不是从零摸索

程序员会先整理上下文，再让 agent 进入执行：

- 哪些文件是关键入口
- 哪些约定必须遵守
- 哪些测试必须通过
- 哪些外部接口不能乱改
- 哪些历史决策不能被破坏

未来优秀程序员的一个重要能力，不是“记住所有代码”，而是“快速给 agent 搭好上下文脚手架”。  
这也是为什么 `AGENTS.md`、`CLAUDE.md`、仓库说明、启动脚本、测试命令会越来越重要：它们本质上是在把隐性经验写成 agent 可执行的环境配置。

### 3. 把任务拆给多个 agent 并行做

很多工作会被拆成多个并行子任务：

- 一个 agent 读代码库并找影响范围
- 一个 agent 起草实现
- 一个 agent 写或补测试
- 一个 agent 做依赖升级或迁移
- 一个 agent 生成 PR 描述、变更摘要和风险说明

这意味着程序员越来越像一个调度者，而不只是执行者。  
未来很常见的状态会是：你本人在本地处理一个关键设计问题，同时几个 agent 在后台各自跑子任务。

### 4. 人类从“直接写”转向“审设计、审风险、审接口”

手写代码不会消失，但它会集中在更关键的位置：

- 架构转折点
- 高风险接口
- 难以形式化的业务规则
- agent 多次失败的复杂问题

也就是说，人类书写会从“大量生产”转向“关键控制”。  
人最有价值的地方，会越来越是提出结构、判断 trade-off、识别“看起来对但其实错”的地方。

### 5. 测试、回归、验证会前移，而且更自动化

未来工作流里，代码生成不是瓶颈，验证才是瓶颈。

所以程序员会更依赖：

- 自动测试
- 回归检查
- 静态分析
- sandbox 执行
- 基准测试
- 代码审计和权限控制

没有验证闭环的团队，会被 AI 放大错误；有验证闭环的团队，会被 AI 放大产能。  
这也是当前主流产品都反复强调 terminal logs、test outputs、sandbox、权限确认的原因：未来真正稀缺的不是“生成”，而是“可信交付”。

### 6. PR 会变成真正的工作汇合点

未来很多代码不是程序员本人一行行写出来的，而是 agent 在分支上完成的。  
因此 pull request 会成为核心节点：

- 看变更是否符合目标
- 看测试和 CI 是否通过
- 看 agent 有没有误解约束
- 看改动是否引入未来维护成本

程序员的重要工作会从“写 PR”转成“评 PR、裁 PR、合 PR”。  
GitHub 已经把这个方向写得很明确：cloud agent 会在 GitHub 上研究仓库、起草计划、在 branch 上改代码、自动建分支和提交，再由人决定何时变成 PR 并合并。

### 7. 日常维护工作会大量异步化

很多今天很碎但很耗时的工作，会优先被 agent 接管：

- 修小 bug
- 升依赖
- 补文档
- 改类型
- 写脚手架
- 处理样板代码
- 追测试失败

这部分工作不会消失，但会从程序员的主工作流里被剥离出去，变成后台并行流水线。  
OpenAI、GitHub 和 Google 都在往同一个方向推：把碎任务从“必须你现在亲手处理”改成“你丢进队列，稍后再审结果”。

### 8. 程序员会更像“软件系统经理”

最终，未来的典型程序员工作流会变成：

1. 选问题
2. 定目标与约束
3. 提供上下文
4. 委托 agent 并行执行
5. 审核方案和风险
6. 运行验证
7. 合并与发布
8. 观察线上反馈
9. 再把新问题送回 agent

所以程序员未来不只是 coder，更像一个高带宽的软件系统经理。

## 团队工作流

如果把视角从单个程序员拉到团队，未来变化会更明显。

### 1. Issue 会变成标准任务接口

越来越多任务会先写成 issue，再交给 agent。  
因为 issue 天然适合承载：

- 背景
- 验收标准
- 文件范围
- 风险边界
- 相关文档和讨论链接

换句话说，未来 issue 不只是管理工具，而是人和 agent 共享的任务接口。

### 2. PR throughput 会成为新的管理指标

GitHub 已经把 Copilot cloud agent 的 pull request 生命周期和 median time to merge 纳入可观测指标。  
这说明未来团队管理不只是看人写了多少代码，而是看：

- 有多少 PR 是 agent 发起的
- 多少被合并
- 多久能完成验证和合并
- 哪类任务适合自动化，哪类不适合

### 3. 团队会分化出新的“工种”

虽然岗位名字未必变化，但职责会变：

- 有人更像 `spec author`，擅长把模糊需求写成 agent 可执行任务
- 有人更像 `review owner`，擅长审 PR、审风险、审边界
- 有人更像 `environment owner`，负责测试、脚本、权限、沙箱、上下文文件
- 有人更像 `complexity closer`，处理 agent 反复失败的难题

未来的“强团队”，不只是高手多，而是这些环节配合得顺。

## 人类职责

未来最不容易外包给 AI 的，不是“写任何代码”，而是以下几类职责：

### 1. 问题定义

到底要解决什么问题，成功意味着什么，哪些 trade-off 可以接受，这仍然是人类主导。

### 2. 架构判断

模块边界、演进方向、长期维护成本、性能与复杂度取舍，不会因为 agent 更强就自动变简单。

### 3. 可信验收

程序员要判断：

- 这个结果是否真的满足需求
- 测试是不是只验证了表面
- 代码是不是在“看起来正确”
- 是否引入了未来难以维护的隐患

### 4. 多方协同

未来软件开发会越来越像在产品、设计、运营、安全、法务、数据和多个 agent 之间做协调。

### 5. 最终责任

agent 可以生成代码，但责任归属、上线判断、事故承担，仍然会落在人和组织身上。

## 边界与失败模式

未来工作流会明显变化，但短期内它也有很硬的边界。

### 1. 任务必须更小、更清楚

METR 在 2025 年 3 月发布的结果说明：按人类专业人员耗时衡量，前沿通用 agent 以 50% 可靠性可完成的任务时长大约每 7 个月翻倍；但当时最强模型的 50% 时间地平线大约只有 1 小时左右，而且“稳健有帮助”的任务往往仍是几分钟级。  
这意味着未来几年里，程序员不是把所有工作整包外包，而是要把工作拆成 agent 能稳定完成的粒度。

这也是 OpenAI 在 2025 年 5 月给 Codex 的内部使用建议里明确写出的：大改动先用 `Ask Mode` 生成实现计划，再切到 `Code Mode`；而且 Codex 最适合那些“你或同事大约一小时能做完”的、边界清楚的任务。

### 2. 没有环境配置，agent 会显著变笨

从 Codex 的最佳实践看，启动脚本、环境变量、网络权限、清晰文档、可靠测试会显著影响结果。  
所以未来一个很现实的事实是：工程环境越混乱，AI 的收益越低。

### 3. “看起来会做”不等于“可以放手做”

今天很多 agent 已经能读仓库、改多文件、跑测试、提 PR。  
但只要任务里包含以下因素，人的介入仍然会显著增加：

- 需求本身模糊
- 多系统耦合
- 线上风险高
- 验收标准不完整
- 测试本身不可信
- 牵涉复杂业务语义

所以未来程序员不是退出回路，而是站到更高一层控制回路。

### 4. 工作流提升高度依赖任务类型

从现有证据看，AI 对程序员的帮助不是均匀分布的：

- 对脚手架、测试、文档、重命名、依赖升级、简单 bug fix，它更容易带来正收益。
- 对熟仓库里的复杂改动、需要深背景知识的任务、验收标准模糊的任务，它未必提速，甚至可能拖慢。

所以未来团队不会问“要不要用 AI”，而会问“哪类任务应该默认交给 AI，哪类不该”。

## 我对未来程序员工作流的判断

我的判断是，未来程序员最像三种角色的叠加：

- 像今天的高级工程师：要懂架构、边界和质量
- 像今天的 tech lead：要拆任务、分配工作、做取舍
- 像今天的工程经理，但更技术化：要管理系统产出，而不只是管理人

因此，未来程序员的核心竞争力会从“手速和 API 熟练度”上移到：

- 问题拆解
- 任务表达
- 上下文构造
- 验证设计
- 风险识别
- 多 agent 协同
- 业务与技术的联合判断

我对工作流形态的更具体判断是：

- 短期：`IDE 共写 + 后台 agent 跑碎任务`
- 中期：`issue / PR 成为 agent-native 的主接口`
- 更长期：`程序员像 orchestrator，一边管理本地探索，一边管理云端任务队列`

## 这不意味着什么

它不意味着：

- 程序员马上消失
- 以后不需要懂底层原理
- 只要会下 prompt 就够了
- agent 能自动承担最终责任

恰恰相反，AI 越强，程序员越需要懂系统、懂约束、懂验证。  
区别只是：未来程序员花时间最多的地方，不再是把每一行代码亲手敲出来，而是确保整个系统被正确、高效、可靠地生产出来。
