
# 开场白 —— 引出问题

请想象这个场景：你用 Claude Code 距离就要完成一个大功能，相伴 AI 已经连续工作了两个小时，突然——它开始犯昨天已经修复过的错误。这很可能就是上下文腐化在作怜。

今天，我们不讲提示词工程，不讲模型能力边界——我们要讲一个香港边界的底层逻辑：上下文窗口的管理。这也是 Anthropic 内部总结的最佳实践。

# 第一部分：搭建认知框架

## 1.1 什么是上下文窗口？

类比：上下文窗口就是 AI 的「短期记忆」。想象一个人在解决问题时能同时记住的所有东西——之前的对话、打开的文件、尝试过的方法、运行过的命令。这就是上下文。

Claude Code 的上下文窗口上限是 100 万 Token。为了直观感受其大小：

• 100 万 Token ≈ 约 75 万英文单词

• 1 个中型 Python 项目（所有源文件 + 文档）消耗大约 5-20 万 Token

• 一次上传大文件就可能消耗数万 Token

## 1.2 上下文腐化：模型的「大脑疲劳」

上下文腐化（Context Rot）是指随着会话伸长，模型的推理质量会逐渐下降。

为什么会这样？类比人类认知：

• 注意力稀释：100 万 Token 都对模型“有吸引力”，相关信息被无关信息“稼释”

• 旧不相关的内容干扰：两小时前的调试输出，现在成了干扰项

• 模型“分心”：就像人在杂乱桂面上大循环，难以专注

关键数据：腐化通常在 30-40 万 Token 时开始显现。这意味着你还没用完 1/3 的上下文，效果就已经开始打折扣。

# 第二部分：核心决策框架 —— 五种选择

每次 Claude 完成一轮任务后，你都处于一个决策节点。这不是巧合，而是一种意识。以下五种路径，选对了事半功倍。

## 选择 1：继续（Continue）——默认模式

何时用：任务连贯，上下文仍然相关，且不到 30 万 Token。

风险：上下文不断堆积，虚耗 Token，模型注意力散漫。

## 选择 2：/rewind 回溯——隐藏的神器

何时用：方案走错、误判断、想重来。

举个实例说明为什么回溯比纠错好：

__场景 A：Claude 读取了 5 个文件，尝试了方案 X，失败。你输入：《那不行，换方案 Y》。结果：失败经过、方案 X 的调试输出全部残留在上下文里，浪费 Token。__

__场景 B：同样的失败。你回溯到「5 个文件读取完毕」节点，重提：《不要用 X，foo 模块没有暴露接口，直接走 Y》。结果：上下文干净，模型全力投入新方向。__

场景 B 的质量几乎必然更高，因为模型没有被干扰。

进阶技巧：回溯前，可要求 Claude “总结从这里开始的关键发现”，得到一个给下一轮的〖交接备忭单〗。类似“未来的自己写信给过去的自己”。

## 选择 3：/compact 压缩——有损的继续

何时用：会话超过 20-30 万 Token，且任务还未完成。

compact 的本质：承认信息损失，但保马河运转。不同于/rewind（时光倒流），/compact 是在原有线索上继续，只是换了一个更精简的记忆层。

主动 vs. 被动 compact：

• 被动（autocompact）：玳目就到，模型处于上下文腐化最严重时自动触发，套用一个“说不清楚”的当前方向导致摘要偏差

• 主动（proactivecompact）：推荐。在模型进入深水区之前主动执行，并附上指导语句，例如：/compact 完成了 auth 重构，下一步要写单元测试

导致糟糕 compact 的典型场景：调试个多小时后 autocompact，摘要里丢失了并提起的其他 warning，然后你说“我们看到了 bar.ts 的那个警告”，Claude 一脸茶马。

## 选择 4：/clear 全新开始——决心的干净

何时用：任务皆点切换时。这是成本，需要你自己写一份「之前会话重点」，也是最高质量的起点。

一份好的会话备忘应包含：

• 当前目标：我们在做什么

• 已确定的约束：不能动 X，不能破坏 Y

• 关键文件：只列必要的2-5 个

• 已排除的方案：这样模型不会重踌覆辙

## 选择 5：子代理——任务隔离

何时用：某段工作会产生大量中间输出，但你只需要结论。

子代理的本质：它就是一个拥有独立上下文窗口的「一次性干活」工具。工作完成后，只把报告个给父代理，它内部生成的所有中间过程全部丢弃。

实用指令模板：

• 「派一个子代理，读取整个代码库，只给我返回以下三点：“核心架构模式”、“主要依赖文件”、“待改进的出口」」

• 「派一个子代理，对这个PR 进行完整 Code Review，返回一份优先级排序的问题列表」

# 第三部分：常见误区与实战跨坑指南

## 误区 1：“100 万 Token 足够，我不需要管理”

这是最常见的误解。100 万 Token 是容量上限，而非最佳工作区间。就像硬盘容量 1TB，不意味着你应该把所有文件堆在一个目录里。

## 误区 2：纠错而非回溯

“不对，你搞错了，再试一次” ——这句话看起来无害，但它将失败轨迹永久写入上下文。多几次之后，上下文里充满了各种失败方案的残迹，模型开始在这些尘埃里搜寻出路。

## 误区 3：错过了主动 compact 的最佳时机

最佳的主动 compact 时机：

• 一个自然语言小里程碑——比如刚完成了 Phase1，准备进入 Phase 2

• 工作模式发生切换——比如处理完问题，要开始写测试

• 上下文达到 20-25 万 Token 时

## 误区 4：坐等 autocompact

训练自己根据上下文展示的 Token 计数主动管理。Claude Code 界面左下角通常会显示当前消耗的 Token 数量。

# 第四部分：建立直觉——两个判断模型

## 模型一：「这是同一任务还是新任务？」

新任务 = 新会话。这是最简单的原则。显而易见的不清晰情形：刻写完一个功能、覆盖完测试，然后想进行下一个功能，这就是新任务。

## 模型二：「我后来还需要这个输出本身，还是只需要结论？」

这是子代理的判断三问题：

• 我需要看完整的文件内容吗？ → 不需要则用子代理

• 我需要和这个文件多轮交互吗？ → 需要则用直接读取

• 我只需要它的结论报告吗？→ 用子代理，保持上下文干净

# 总结：实操清单

把这张清单贴在工作区旁边，直到它成为局能：

• [ ] 开始新任务前：/clear+ 写简备忘

• [ ] 工作中造得错：优先考虑/rewind，不是纠错

• [ ] 会话达 20 万 Token：考虑主动/compact + 方向说明

• [ ] 一次性大量分析任务：用子代理

• [ ] 每个自然语言小里程碑后：评估是否需要 /compact

上下文管理是 Claude Code 最容易被忽视、收益也最显著的一项技能。掌握它，你能让模型始终处于「小白窗」状态。
