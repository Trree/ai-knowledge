# Gemini Deep Research 运行机制研究笔记

## 一、完整运行步骤（双层视角）

### 用户可见层：5 个步骤

#### 步骤一：意图拆解与多维约束重构

不是简单理解用户问了什么，而是通过**四维框架**解构问题：

| 维度       | 作用                                       |
| -------- | ---------------------------------------- |
| **主题与范围** | 界定核心对象和外延边界，防止在海量数据中迷失                   |
| **时间维度**  | 提取数据时效性要求（如"最近两年"、"最新趋势"）                |
| **特定基准**  | 识别潜在的横向对比维度（定价、技术规格、合规性等）                |
| **输出格式**  | 预判最终呈现形式（时间轴、对比矩阵、雷达图等）                  |

这四个维度构成后续计划生成的**约束条件**。

#### 步骤二：研究计划生成与边界锚定

系统生成多级大纲形式的研究计划，展示：
- 计划调查的子主题
- 预期信息来源
- 逻辑推演方向

用户可审阅、删除分支、补充缺失项、调整权重。**确认后才进入执行。**

#### 步骤三：自主信息寻源与跨域深度浏览

- 自主发起约 **80 次搜索**（复杂任务可达 **160+ 次**）
- 不仅搜公共网络，还穿透 Google Workspace 私有数据（Gmail/Drive/Docs/Sheets）
- 自主阅读并消化**上百页异构文档**
- 耗时数分钟到数十分钟

#### 步骤四：长上下文推理与去重综合

- 利用百万级 Token 上下文窗口，**全部信息同时加载**
- 执行去重、实体解析、矛盾消解
- 根据信息源权威性和时间戳进行**权重仲裁**
- 界面实时展示"思考过程（Thinking Summaries）"

#### 步骤五：多模态报告生成与交互式输出

- 结构化报告 + 内联引文（每项断言可溯源）
- 自动生成图像、架构图、交互式图表
- 可导出为 Google Docs / 音频摘要
- 可进入 Canvas 二次编辑，或继续追问深挖

### 底层机制层

#### 智能体循环（Agentic Loop）

四步闭环不断迭代：

```
感知 → 推理 → 行动 → 观察 → 感知 → ...
      （while 循环，直到无更多函数调用需求）
```

#### GVR 对抗架构

每一轮输出都经过内部博弈：

```
生成器（提出假设/策略）
  → 验证器（审查事实矛盾/逻辑断裂/幻觉）
    → 修正器（调整输出/重新规划路径）
```

数轮甚至数十轮自我纠错后，才呈现给用户。

#### 搜索算法三大机制

| 机制          | 说明                                      |
| ----------- | --------------------------------------- |
| **因果链导航**   | 步骤 A 的结果决定步骤 B 的搜索关键词，层层递进              |
| **死胡同检测与回溯** | 类 DPLL 算法的深度优先搜索，识别无效路径后退回枢纽点，换分支重新探索   |
| **停止标准内省**   | 多条并行探索路径 + 多数投票/加权投票，边际收益趋零时果断停止        |

#### 长上下文管理

- **百万级窗口**：一次性加载约 1500 页文本，克服"迷失在中间"效应
- **上下文缓存**：50%-70% 的 Token 通过缓存复用，单次任务成本控制在 $3-5
- **代码执行桥接**：遇到数理分析时自主编写 Python 代码在沙箱中运行

## 二、研究计划生成的原则

### 原则一：四维分析框架

在生成计划前，系统通过主题与范围、时间维度、特定基准、输出格式四个维度解构问题，形成后续计划的约束条件。

### 原则二：先规划后执行 + 人机协同

- 系统以多级大纲形式呈现计划
- 展示子主题、预期信息来源、逻辑推演方向
- 用户可删除无关分支、补充缺失项、调整权重
- 目的是"将模型拉回人类认知框架内"

### 原则三：可搜索性导向

每个子任务最终要转化为可执行的搜索查询（约 80-160 次独立搜索）。每个分支必须能被分解为具体的、可通过网络检索回答的问题。

### 原则四：GVR 自检机制

计划本身也受到生成器-验证器-修正器（GVR）架构的约束——生成后经内部验证器审查逻辑完备性，修正器修补盲点，再呈现给用户。

### 与通用推断的对比

| 维度       | 通用推断（MECE等）          | Gemini 实际实现                    |
| -------- | -------------------- | ------------------------------ |
| 分解方法     | MECE 原则              | **四维分析框架**（更结构化）               |
| 隐含维度补全   | 基于 LLM 世界知识          | **"特定基准"维度**（主动识别潜意识对比需求）      |
| 以终为始     | 预设报告骨架               | **"输出格式"预判**（时间轴/对比矩阵/雷达图）    |
| 可搜索性     | 叶子节点可搜索              | 同，且量化了 **80-160 次搜索**          |
| 用户校准     | 人机协作校准点              | 完全一致，称为**"边界锚定"**              |
| 自检机制     | 未涉及                  | **GVR 对抗架构**验证计划质量             |

## 三、Agentic 搜索循环详解

### 核心结构

本质上是一个 `while` 循环——持续运行，直到无更多函数调用需求：

```
while (还有未完成的子任务 || 置信度未达阈值):
    感知(Perception)
    推理(Reasoning)
    行动(Action)
    观察(Observation)
```

### 四步闭环

#### 1. 感知（Perception）

每轮循环开始时，智能体同时吸收两类输入：

- **目标状态**：用户的最终研究目标 + 当前未完成的子任务清单
- **环境状态**：上一轮搜索返回的网页内容 / API 数据 / 内部文档

感知不是被动接收，而是**有选择性地注意**——根据当前子任务的需要，从百万 Token 的上下文窗口中提取相关片段，忽略噪音。

#### 2. 推理（Reasoning）

基于感知结果，通过链式思考（CoT）或 ReAct 框架做两件事：

**a) 子任务降维**：将宏观目标拆解为当前这一步可执行的具体动作

```
宏观目标："调查 X 公司的核心技术团队背景"
     ↓ 降维
当前子任务："在 GitHub 上搜索 X 公司代码库的核心贡献者"
```

**b) 策略选择**：决定用什么工具、什么查询语法、去哪个数据源

#### 3. 行动（Action）

调用具体工具执行原子操作：
- 发起搜索引擎查询
- 打开并阅读网页
- 调用 Google Workspace API
- 运行 Python 代码
- 通过 MCP 协议访问第三方系统

#### 4. 观察（Observation）

对行动返回的结果进行严格评估，产生三种判断：

| 判断       | 后续动作                          |
| -------- | ----------------------------- |
| **子任务完成** | 标记完成，进入下一个子任务，开始新一轮循环         |
| **需要追问**  | 基于当前结果生成 follow-up 查询，继续本轮循环  |
| **陷入死胡同** | 触发回溯机制，退回枢纽点，换路径              |

### 三大搜索机制

#### 机制一：因果链导航（Causal Chain Navigation）

信息是链式依赖的，每一步的搜索关键词依赖上一步的结果：

```
轮次1: 搜索 "X公司早期项目"
   → 发现行业论坛提到项目代号 "Project Alpha"

轮次2: 搜索 "Project Alpha GitHub"
   → 发现代码库，提取核心提交者邮箱 john@x-corp.com

轮次3: 搜索 "john@x-corp.com LinkedIn"
   → 锁定核心研发人员背景

轮次4: 搜索该人员的学术论文
   → 发现其技术路线的理论源头
```

#### 机制二：死胡同检测与故障感知回溯

采用类 DPLL 算法的深度优先搜索策略：

```
搜索树示意：

研究目标
├── 分支A：行业报告路线
│   ├── A1: 搜索行业白皮书 → 找到3篇 ✓
│   ├── A2: 深入某篇白皮书的引用 → 付费墙 ✗
│   └── A3: 换数据库搜索 → 内容重复 ✗
│         ↑ 死胡同 → 回溯到分支A根节点
│
├── 分支B：学术论文路线 ← 回溯后切换
│   ├── B1: Google Scholar → 找到核心论文 ✓
│   └── B2: 追踪引用网络 → 发现新证据 ✓
│
└── 分支C：社交媒体/论坛路线
    └── ...
```

**死胡同判定标准**：
- 连续 N 步搜索无新信息增益
- 返回内容与已有信息高度重复
- 遇到付费墙/访问限制/404
- 信息质量明显低于可信阈值

**回溯动作**：撤销无效操作 → 退回枢纽点 → 重构查询/换数据源/调整假设 → 沿新分支展开

#### 机制三：停止标准内省

```
并行采样策略：

路径1: 搜索路线 A → 证据集 {e1, e2, e3}
路径2: 搜索路线 B → 证据集 {e2, e4, e5}
路径3: 搜索路线 C → 证据集 {e1, e3, e5, e6}
            ↓
    聚合：多数投票 / 加权投票 / Best-of-N
            ↓
    置信度评估：信息集是否全面？边际收益是否趋零？
            ↓
       是 → 停止搜索    否 → 继续循环
```

**两种失效模式的防御**：

| 失效模式     | 表现              | 防御机制                 |
| -------- | --------------- | -------------------- |
| **过早停止** | 数据召回率低，遗漏关键信息   | 多路径并行 + 交叉验证不充分时不停止  |
| **对冲行为** | 盲目收集低置信度信息提高召回率 | 加权投票过滤低质量证据          |

### GVR 对抗架构（贯穿每一轮）

不是循环结束后才验证，而是每一轮都在博弈：

```
生成器(G)：
  "根据当前信息，我认为应该搜索 'X公司2024年营收'"

验证器(V)：
  "上一轮已从年报获取营收数据，搜索会重复。
   且用户问的是技术团队，不是财务，方向偏移。"

修正器(R)：
  "修正：改为搜索 'X公司CTO技术演讲2024'，
   更贴近用户真实意图。"

→ 执行修正后的行动
```

### 单轮循环完整示意

│                    一轮循环                          │

│   │          │  ↑         │           │             │

│   │          │  │G→V→R     │           │             │

## 四、与其他系统的本质区别

```
普通搜索：  问题 → 一次搜索 → 返回链接列表
RAG：      问题 → 向量检索 → 拼接上下文 → 生成回答
Deep Research：问题 → 四维拆解 → 研究计划 → 多轮自主搜索/浏览 → GVR自检 → 综合分析 → 结构化报告
```

本质区别：不是"搜索一次返回结果"的单次交易，而是一个**具备因果推理、自我纠错、动态回溯、主动停止能力**的持续运转闭环。80-160 次搜索不是预先规划好的，而是循环在运行过程中**动态生成**的。

## Agentic 搜索循环详解

### 宏观架构

整个循环可以拆成 **3 层嵌套 loop**：

```
外层 Loop：遍历研究计划中的每个子问题
  中层 Loop：对单个子问题进行多轮搜索直到信息充分
    内层 Loop：对单次搜索结果中的多个网页逐一阅读评估
```

---

### 外层 Loop：子问题调度

```
研究计划 = [子问题1, 子问题2, ..., 子问题N]
已收集知识库 = {}

for 子问题 in 研究计划:
    result = 中层Loop(子问题, 已收集知识库)
    已收集知识库.merge(result)
    
    // 关键：动态计划修正
    if result 中发现了计划外的重要线索:
        研究计划.append(新的子问题)
    if 某个后续子问题已被当前结果覆盖:
        研究计划.skip(该子问题)
```

**核心机制——动态计划修正**：

比如研究"mRNA 疫苗技术"，原计划没有"脂质纳米颗粒递送"这个子问题，但在阅读某篇文章时发现这是关键瓶颈，就会**动态插入**一个新子问题。

反过来，如果子问题 3 的答案在研究子问题 1 时已经顺带获得了，就**跳过**。

---

### 中层 Loop：单个子问题的搜索策略

这是最核心的部分。对每个子问题执行一个**自主决策循环**：

```
def 中层Loop(子问题, 已有知识):

    搜索轮次 = 0
    该问题的信息池 = []
    
    while True:
        搜索轮次 += 1
        
        // ① Query 构造
        if 搜索轮次 == 1:
            query = 从子问题直接生成搜索词
        else:
            query = 基于(子问题 + 已有结果的缺口)生成 follow-up 搜索词
        
        // ② 执行搜索
        搜索结果 = Google_Search(query)
        
        // ③ 网页阅读（内层 Loop）
        新信息 = 内层Loop(搜索结果, 子问题)
        该问题的信息池.append(新信息)
        
        // ④ 充分性判断（关键决策点）
        判断 = 评估信息充分性(子问题, 该问题的信息池)
        
        if 判断 == "充分":
            break
        elif 判断 == "部分缺失":
            // 生成针对性的补充 query，继续循环
            continue
        elif 判断 == "方向错误":
            // 换一个完全不同的搜索角度
            重置搜索策略()
            continue
        elif 搜索轮次 > 上限:
            // 避免无限循环，标记为"尽力而为"
            break
    
    return 该问题的信息池
```

#### ① Query 构造策略

不是简单地把子问题复制粘贴成搜索词，而是有**多种 query 生成策略**：

```
子问题："锂电池在极寒环境下的性能衰减"

第1轮（直接搜索）：
  → "lithium battery performance cold weather degradation"

第2轮（发现缺具体数据）：
  → "lithium ion battery capacity loss -20°C percentage study"

第3轮（需要对比视角）：
  → "LFP vs NMC battery cold weather performance comparison"

第4轮（追踪到一个关键实验室）：
  → "Idaho National Laboratory battery cold testing results 2024"
```

策略类型：

|策略|触发条件|示例|
|---|---|---|
|**直接搜索**|首轮|子问题原文转 query|
|**精确化**|结果太泛|增加限定词、年份、具体指标|
|**换角度**|当前角度饱和|从学术→产业，从中文→英文|
|**追源头**|发现关键引用|搜索原始论文/机构/数据集|
|**对比验证**|信息冲突|搜索"X vs Y"或第三方评测|
|**反向搜索**|需要反面证据|搜索"X 缺点/批评/争议"|

#### ④ 充分性判断（最关键的决策）

这是区分 Deep Research 和普通搜索的**核心智能**。模型需要判断：

```
已有信息是否足以回答这个子问题？

评估维度：
┌──────────────────────────────────────────┐
│ 1. 覆盖度：关键方面是否都有涉及？          │
│    → "成本对比只找到了购置价，缺运营成本"   │
│                                          │
│ 2. 可信度：来源是否足够权威？               │
│    → "只有博客说法，缺学术/官方数据"        │
│                                          │
│ 3. 一致性：多个来源是否相互印证？            │
│    → "两个来源数据矛盾，需要第三方验证"     │
│                                          │
│ 4. 时效性：信息是否足够新？                 │
│    → "最新数据是2022年的，需要更新"         │
│                                          │
│ 5. 深度：是否有足够的细节支撑论述？          │
│    → "有结论但缺原因解释"                   │
└──────────────────────────────────────────┘
```

判断结果映射到行动：

```
所有维度通过 ──────────→ 标记完成，进入下一子问题
覆盖度不足 ────────────→ 生成补充 query（针对缺失方面）
可信度不足 ────────────→ 搜索更权威来源（论文、官方报告）
一致性冲突 ────────────→ 搜索第三方/meta-analysis 验证
时效性不足 ────────────→ 加上年份限定重新搜索
深度不足 ──────────────→ 搜索 "why" / "mechanism" / "详解"
```

### 内层 Loop：网页阅读与信息提取

```
def 内层Loop(搜索结果, 子问题):
    
    提取的信息 = []
    
    for 网页 in 搜索结果.top_results:
        
        // ① 预筛选（不是每个都读）
        if 网页.snippet 明显不相关:
            skip
        if 网页.域名 已知低质（内容农场等）:
            skip
        
        // ② 读取网页内容
        页面内容 = fetch_and_parse(网页.url)
        
        // ③ 定向提取（不是读全文）
        相关段落 = 从页面内容中提取与子问题相关的部分
        
        // ④ 信息评估
        评估 = {
            "事实性": 是否包含可验证的事实/数据,
            "来源质量": 域名权威性 + 作者专业性,
            "新增价值": 相对于已有信息是否提供了增量,
            "引用价值": 是否值得在最终报告中引用
        }
        
        if 评估.新增价值 > 阈值:
            提取的信息.append({
                "内容摘要": 相关段落的压缩版,
                "原始URL": 网页.url,
                "可信度评分": 评估.来源质量,
                "关键数据点": 提取的具体数字/结论
            })
    
    return 提取的信息
```

**关键点——不是"读完所有网页"，而是"选择性阅读+定向提取"**。长上下文窗口（1M tokens）让它可以在内存中保持大量已读内容，但它仍然会做筛选以提高效率。

### 跨子问题的知识传递

这是三层 loop 之间最精妙的连接：

```
研究子问题1："电动车购置成本"
  → 收集到：特斯拉降价信息、比亚迪价格区间、补贴政策

研究子问题2："电动车日常使用成本" 
  → 搜索时，模型已经知道子问题1中涉及的具体车型
  → 自动将 query 锚定在相同车型上，保证报告的一致性
  → 如果子问题1中某篇文章顺带提了使用成本，直接复用，不重复搜索

研究子问题3："残值与贬值"
  → 发现特斯拉频繁降价严重影响残值
  → 回溯标注：这与子问题1的"降价"信息形成因果链
  → 最终报告中会将这两点关联呈现
```

### 异常处理与保护机制

```
// 防止无限循环
MAX_SEARCHES_PER_SUBTOPIC = ~10
MAX_TOTAL_SEARCHES = ~100
MAX_TOTAL_TIME = ~10 minutes

// 防止信息冲突僵局
if 同一问题搜索 > 5次仍有矛盾:
    标记为"存在争议"，在报告中呈现多方观点
    而非继续搜索试图找到"正确答案"

// 防止深度陷阱（rabbit hole）
if 某个子问题消耗了 > 30% 的总搜索预算:
    强制结束，标记为"已尽力覆盖"
    将剩余预算留给其他子问题

// 搜索失败处理
if 某个 query 返回结果极少:
    尝试放宽搜索词
    尝试英文搜索（如果原来是中文）
    仍无结果 → 在报告中标注"公开信息有限"
```

**一句话总结**：整个 Agentic 循环的灵魂在于**充分性判断**——它不是"搜一次就完事"，而是每搜一次都反问自己"够了吗？还缺什么？"，这个自我评估能力是靠 LLM 的推理（CoT）实现的。
