一、核心命题：从「写代码」到「写指令」

  [[autoresearch]] 的根本转变是——人类研究者的工作从写训练代码，变成了写「指导 AI 如何做研究」的指令文件。

  项目只有三个核心文件：
  - prepare.py — 不可变的评测基础设施（人类定义的"游戏规则"）
  - train.py — AI 唯一可以修改的文件（实验本体）
  - program.md — 人类写给 AI 的研究方法论（"元程序"）

  [[Karpathy]] 原话的精髓：你不再直接碰 Python 训练代码。你在编程的是 program.md——你在编程那个程序员。

  这是一种**元编程（meta-programming）**的思想：人类退后一层，从"做研究"变成"设计研究过程"。

  ---
  二、Karpathy 一贯的「Software 2.0」思想的自然延伸

  Karpathy 在 2017 年提出「Software 2.0」：神经网络的权重取代手写逻辑，成为真正的"程序"。

  Autoresearch 是这个思想的递归应用——现在不仅模型的权重是"学"出来的，连训练模型的代码本身也交给 AI 去"搜索"和"进化"了。可以类比为：

  ┌──────────┬──────────┬──────────────┬─────────────────┐
  │   层级   │ 传统方式 │ Software 2.0 │  Autoresearch   │
  ├──────────┼──────────┼──────────────┼─────────────────┤
  │ 推理逻辑 │ 人写规则 │ 网络学习     │ 网络学习        │
  ├──────────┼──────────┼──────────────┼─────────────────┤
  │ 训练代码 │ 人写代码 │ 人写代码     │ AI 写代码       │
  ├──────────┼──────────┼──────────────┼─────────────────┤
  │ 研究方法 │ 人的直觉 │ 人的直觉     │ 人写 program.md │
  └──────────┴──────────┴──────────────┴─────────────────┘

  这是 Software 2.0 思想的再上一层——Software 3.0：连制造 Software 2.0 的过程都自动化了。

  ---
  三、极简主义作为第一原则

  这个项目处处体现 Karpathy 标志性的「从零构建、剥离到本质」风格：

  - 整个项目就 3 个文件，没有 CLI 参数，没有配置文件，没有分布式训练
  - 一块 GPU，一个文件，一个指标（val_bpb）
  - 给 AI 的指令里明确写道："同等条件下，更简单的更好。一个小改进如果带来丑陋的复杂度，就不值得。反过来，删掉什么东西还能保持效果，这是好结果。"

  这和 micrograd（一个极简自动微分引擎）、nanoGPT 是同一脉思想——理解的深度来自极致的简洁。但 autoresearch 将这个原则从"教学工具"升级为了"自动化研究框架"。

---
  四、固定时间预算 = 公平的搜索空间

  每个实验被严格限制在 5 分钟墙钟时间内。这个设计极其精巧：

  - AI 可以改任何东西（模型深度、batch size、架构、优化器）
  - 但结果仍然直接可比，因为时间预算恒定
  - 指标用 bits-per-byte（词表无关），进一步消除了变量

  这创造了一个公平、封闭的搜索空间——像是给 AI 设计了一个"科学实验室"，所有变量都受控，只看最终结果。

  ---
  五、贪心爬山 + Git 作为状态机

  实验循环本质是贪心局部搜索（greedy hill climbing）：

  1. 改一下 → 跑 5 分钟 → 看指标
  2. 比上次好 → 保留 commit，推进分支
  3. 不好 → git reset，丢弃
  4. 永不停止，循环到人类醒来打断

  Git 分支就是搜索的状态指针。results.tsv 是 append-only 的实验日志但不入 git——代码历史和实验历史分离。

  这背后是一种务实的研究哲学：不需要复杂的搜索算法（贝叶斯优化、进化策略等），AI agent 本身的"直觉"（LLM 的知识）就是启发式，贪心就够用了。

  ---
  六、「永不停止」——自主性作为核心设计目标

  program.md 里有一条全大写的指令："NEVER STOP"。

  ▎ "人类可能在睡觉。你是自主的。如果你没想法了，想得更努力一点。循环一直跑到人类打断你为止。"

  这不是一个"助手"，而是一个自主研究者。这反映了 Karpathy 对 AI agent 的定位：不是对话式的问答工具，而是可以独立运转的劳动力。在他的 Tesla
  经历中（垂直整合的端到端系统），同样体现了对"自主、闭环"系统的偏好。

  ---
  七、实证结果：它确实有效

  样例运行显示：83 次自主实验中，15 次产生了真实改进，val_bpb 从 ~0.998 降到 ~0.977（约 2.1% 的提升）。AI 自主发现的改进包括：

  - 减半 batch size（换取更多更新步数）
  - 增加 warmdown 比例和 warmup
  - 加深网络（8→9层）
  - 调整 RoPE 频率基数（10K→200K）
  - 改变滑动窗口注意力模式

  这些不是随机搜索能找到的——它们体现了对训练动态的理解，说明 LLM 确实具备一定的 ML 研究"直觉"。
  
  ---
  总结：一句话概括

  Autoresearch 的核心思想是：当 AI 足够强时，人类研究者的最高杠杆点不再是「写更好的代码」，而是「写更好的指令」——定义好搜索空间、评价标准和方法论，然后让 AI 在这个空间里自主探索。

  这是 Karpathy 整个职业生涯思想的汇聚：Stanford 的教育简洁性 × Tesla 的端到端系统观 × OpenAI 的大模型能力 × 一贯的极简主义 → 最终指向「AI 做 AI 研究」这个自指的终点。



现在能将这种思想用于哪种地方

● 这个问题的本质是：「固定评测标准 + AI 自主循环改进 + 贪心保留」这个范式，还能套在哪些场景上？

  关键前提是——能套用的场景必须满足三个条件：

  1. 有一个可自动计算的、单一的评价指标（相当于 val_bpb）
  2. 修改空间在一个文件/模块内，改完能自动跑（相当于 train.py）
  3. 每次实验的成本可控、时间有限（相当于 5 分钟预算）

  满足这三条的场景其实非常多——

  ---
  一、直接可套用的场景

  1. 编译器/代码生成优化

  - 改什么：编译器的 pass 顺序、指令选择策略、寄存器分配算法
  - 评什么：benchmark 程序的执行时间或二进制大小
  - 时间预算：编译 + 跑 benchmark，几分钟一轮
  - 这和 autoresearch 几乎同构。LLVM 的 pass pipeline 就是一个巨大的可搜索空间，目前主要靠人类专家调。

  2. Prompt Engineering 自动优化

  - 改什么：一个 prompt.md 文件
  - 评什么：在标注测试集上的准确率/F1
  - 时间预算：跑一批 API 调用，几分钟
  - 已经有人在做（DSPy、ADAS），但 autoresearch 的范式更干净：让 coding agent 直接改 prompt 文件、跑评测、git 保留/回滚。

  3. SQL 查询 / 数据管道性能调优

  - 改什么：查询写法、索引策略、ETL 逻辑
  - 评什么：查询延迟、吞吐量
  - 时间预算：跑一次 benchmark query 几秒到几分钟
  - DBA 日常做的事，完全可以让 AI 在一个 queries.sql 上自主循环改进。

  4. 前端性能优化

  - 改什么：组件实现、打包配置、渲染策略
  - 评什么：Lighthouse 分数、LCP/FID/CLS 等 Core Web Vitals
  - 时间预算：build + Lighthouse 审计，几分钟一轮
  - 指标完全自动化，搜索空间在代码里，天然适配。

  5. 游戏 AI / 策略参数调优

  - 改什么：AI 的决策逻辑、权重、启发式参数
  - 评什么：对局胜率（自我对弈或 vs 基线）
  - 时间预算：跑 N 局模拟，几分钟
  - 棋类、RTS、卡牌游戏的 AI 都适用。

  ---
  二、稍作改造就能用的场景

  6. 芯片设计（EDA）

  - 改什么：RTL 代码、布局参数
  - 评什么：面积 × 延迟 × 功耗（PPA）
  - 难点：单次综合耗时较长（分钟到小时），但可以用快速估算工具替代完整综合
  - Google 已经用 RL 做芯片布局，autoresearch 范式可以做得更上层——直接改 Verilog。

  7. 配方/材料配比优化

  - 改什么：一个 recipe.yaml（成分比例、工艺参数）
  - 评什么：模拟器预测的材料性能（强度、导电性等）
  - 时间预算：一次模拟几秒到几分钟
  - 制药（分子模拟）、新材料、化工配方，只要有靠谱的模拟器就能套。

  8. 基础设施配置调优

  - 改什么：Kubernetes 资源配置、数据库参数（postgresql.conf）、JVM 参数
  - 评什么：吞吐量、P99 延迟、资源利用率
  - 时间预算：压测几分钟
  - 目前这些参数基本靠运维经验和零散博客，非常适合自主搜索。

  9. 算法竞赛 / LeetCode 自动刷分

  - 改什么：算法实现
  - 评什么：正确性（全通过）+ 运行时间排名
  - 时间预算：提交 + 获得结果，秒级
  - 让 AI 反复改一道题的解法，贪心保留更快的实现。

  ---
  三、更深层的思想迁移

  上面都是"直接套模式"。但 autoresearch 更深层的思想——人类从执行者退为设计者——可以应用到更抽象的层面：

  10. 「Research Manager」模式

  不只是调参。人类写一个 program.md 定义：
  - 研究问题是什么
  - 可以读哪些论文（通过工具）
  - 如何设计实验
  - 如何评判结果

  然后 AI 自主执行完整的研究循环：读文献 → 提出假设 → 写代码验证 → 分析结果 → 提出下一步。这是 autoresearch 的终极形态。

  11. 「课程设计」自动优化

  - 改什么：教学材料、习题、讲解顺序
  - 评什么：学生测试成绩（A/B 测试）
  - 这很契合 Karpathy 的教育背景——用他自己发明的范式来优化他最在乎的事。

  ---
不适用的场景（反面边界）

  标注清楚什么不能用，同样重要：

  - 没有自动化评价指标的（如"这个 UI 好不好看"、"这篇文章写得好不好"）——除非你能把主观评判转化为可计算的代理指标
  - 单次实验成本极高的（如真实物理实验、大规模分布式训练）——5 分钟预算是关键，太贵就不能贪心搜索
  - 搜索空间不在代码/文本里的（如机械结构优化）——除非有参数化建模

  ---
  一句话总结

  >任何「能写成文件、能自动评分、能几分钟跑完」的优化问题，都能套 autoresearch 范式。 核心不是具体领域，而是你能不能把问题压缩成：一个可编辑文件 + 一个自动指标 + 一个时间预算。
