## ⏱️ 背景

### ① 相关工作背景情况

我们日常用 AI 辅助开发时，已经有了不少好用的 skill：先头脑风暴确认设计，再生成实现计划，然后按计划执行、测试、review。

单看每个 skill 都能干活。问题在于，团队真实落地时，常常需要把多个 skills——开发规范、内部代码资产复用、专项审查、测试验证、发布确认——组合起来，而每次组合都靠人手工拼。

Skill 工作流编排系统要解决的就是这个”组合层”问题：把多个 skills 编排成可运行 workflow，让团队可以通过 `/workflow:*` 命令直接创建、运行、恢复、对比和复用流程。

核心能力包括：

- 用 YAML 定义 workflow，支持 `steps`、`depends_on`、`gate`、`inputs`、`outputs`。
- 通过 Claude Code plugin 分发 `/workflow:init`、`/workflow:list`、`/workflow:create`、`/workflow:run`、`/workflow:compare`。
- 保存 `.workflow/runs/` 运行记录，支持状态持久化和断点恢复。
- 支持 Skill Swap 和同输入 A/B 对比。
- 内置 `workflow-validator` 和 `diff-reporter`，用于校验流程和生成对比报告。

### ② 传统方式痛点

这里的“传统方式”不是指完全不用 Superpowers，而是指：**有 Superpowers 和各种 skills，但每次组合、定制、复用仍然靠人手工处理。**

| 痛点                        | 具体表现                                         | 影响                  |
| ------------------------- | -------------------------------------------- | ------------------- |
| Superpowers 能锁顺序，但定制流程不方便 | 如果要加入内部 skill、专项审查、发布 gate，需要额外改规则、补命令或手工约定  | 团队很难快速生成适合自己业务的 SOP |
| skills 很多，但组合成本高          | 需要人工判断先用哪个 skill、后用哪个 skill、怎么传递上下文          | 流程容易因人而异，复用成本高      |
| SOP 写在文档里，但不能直接运行         | 文档说明了流程，系统不会自动按流程执行、保存状态、恢复失败步骤              | 执行仍靠人记，交接和复盘成本高     |
| 中断后难恢复                    | 长任务失败或暂停后，需要从聊天上下文里找当前进度                     | 重跑成本高，容易丢失中间产物      |
| 单步优化缺少可靠对比                | 想换一个 review skill 或 plan skill，但不同输入下对比结果不可靠 | 优化容易变成主观感受          |

### ③ AI 介入后的预期和实际效果

预期效果：不是替代 Superpowers，而是把 Superpowers 这类最佳规范、团队内部 skills 和业务 SOP 组合成可运行、可恢复、可对比、可复用的 workflow。

实际效果：WeaveSpec 已经把“开发规范”提升为“流程运行时”。它让团队可以把 spec mode、API 开发、后端功能开发、内容发布等流程沉淀成 workflow 模板，并在不同项目中复用。

### AI 使用前后对比

| 环节 | 之前（原工作流） | 以前所需时间/投入及产出效果 | 现在（使用 WeaveSpec 后） | AI 介入后所需时间/投入及产出效果 | 效率/质量提升 |
|---|---|---|---|---|---|
| 流程组合 | 手工把 Superpowers、内部 skill、审查 skill 拼在一起 | 每次都要重新判断顺序和衔接方式；产出依赖个人经验 | 用 `/workflow:create` 选择 skills 并生成 workflow YAML | 一次配置，多次复用；流程结构可审查 | 降低组合成本，减少因人而异 |
| 流程运行 | 按聊天上下文逐步调用 skill | 长任务容易中断，进度不清晰 | 用 `/workflow:run <name>` 按 DAG 依赖执行 | 自动按步骤运行，输出运行摘要 | 执行路径稳定 |
| 中断恢复 | 失败后人工翻上下文 | 容易重跑或漏步骤 | `.workflow/runs/` 保存 `state.yaml` 和步骤输出，支持 `--resume` | 从最近失败/暂停点继续 | 降低恢复成本，过程可追溯 |
| 质量优化 | 凭感觉换 prompt 或 skill | 很难判断是 skill 差异还是输入差异 | `/workflow:compare` 在同一输入下比较两个 skill 或变体 | 生成对比输出和报告 | 对比更可信，优化更聚焦 |
| 团队 SOP | 流程写在文档中 | 文档可读但不可运行 | workflow 模板随插件分发 | 团队成员可直接初始化并运行 | SOP 从说明文档变成可执行资产 |
| 人工确认 | 每一步都可能被打断确认 | 人被拉回流水线质检员位置 | gate 只放在方向分叉和不可逆动作前 | 减少无效中断，保留关键判断 | 注意力用在关键点 |

## 📌 使用案例：接手线上服务，用工作流完成新功能开发

### 项目背景

我刚接手 actrewarddivide（奖池瓜分服务）。这是一个已经在跑的线上服务，负责各类活动中的奖池配置、用户瓜分资格、奖励计算与发放。技术栈是 Java 21 + Spring Boot + Dubbo，代码量中等（约 6000 行），但奖励计算逻辑涉及多种瓜分模式、保底机制、加倍卡等交叉规则，改动时需要确保不影响现有线上模式。项目文档有限，主要靠读代码理解业务逻辑。

### 需求

活动需要新增一种瓜分模式：从 N 个用户中随机选一个发奖。

看起来简单，但实际要考虑：
- 新模式怎么和现有的奖励计算逻辑兼容
- 随机选取的公平性怎么保证
- 怎么确保不影响其他瓜分模式的线上行为

### 执行方式

全程使用已编排好的 backend-dev 工作流，一条命令跑完：

```
/workflow:run backend-dev “为actrewarddivide新增随机选一人的瓜分模式”
```

工作流按 DAG 依赖自动执行以下阶段：

- **设计和规划**：brainstorming + writing-plans，先想清楚再动手
- **资产复用分析**：扫描项目中已有的可复用代码
- **开发执行**：TDD 方式，先写测试再实现
- **质量检查**：verification + Karpathy guidelines + 金额流转审查

### 阶段一：设计和规划

brainstorming 帮我把模糊的”随机选一人”翻译成了精确的技术方案：在哪改、怎么改、不改什么。

writing-plans 产出了完整的实现计划：

- **需求映射**：把每条需求对应到具体代码落点
- **文件范围**：只改 RewardCalcUtil（奖励计算）、DivideTypeEnum（枚举）、PoolConfig（配置注释）、RewardCalcUtilTest（测试）4 个文件
- **边界约束**：不改库存获取逻辑、不改结算发奖链路、不改流水记录

对刚接手项目的人来说，这个”不改什么”的边界比”改什么”更重要。

### 阶段二：资产复用分析

自动扫描确认了项目中已有的可复用代码：`RewardSessionService` 已有库存获取方法，结算和发奖链路可以完全复用。不需要重新造轮子，只需要在 `RewardCalcUtil` 中新增一个随机选取的分支。

### 阶段三：开发执行

工作流按 TDD 方式执行：

**先写失败测试**：验证新瓜分模式的行为——随机选一人、每人最多中奖一次、正贡献用户耗尽后停止。运行测试，果然失败。

**实现新算法**：在 `RewardCalcUtil` 中新增随机选取逻辑，用安全随机数从候选用户中抽取。运行测试，全部通过。

**更新兼容性**：在枚举中新增 divideType，更新配置注释，确保与现有模式兼容。

### 阶段四：质量检查

工作流自动运行多层检查：

- **Karpathy guidelines**：确认改动精准，没有重构无关代码
- **金额流转审查**：确认奖励份数仍使用整数类型，没有改变事务边界
- **回归测试**：全模块测试通过，现有瓜分模式不受影响

### 成果

| 产出 | 具体内容 |
|---|---|
| 实现计划 | 完整的需求映射、文件范围、分步 task |
| 修改文件 | 4 个：奖励计算、枚举、配置、测试 |
| 测试覆盖 | 新增多个测试用例，全部通过 |
| 质量检查 | guidelines 通过、金额审查通过、全模块回归通过 |

### 关键体会

1. **规划最有价值**：刚接手项目，对代码不熟。工作流逼着我在动手前就把”不改什么”想清楚了。
2. **TDD 给信心**：对线上服务做改动，先写测试再实现，改完跑一下就知道对不对。
3. **质量检查自动化**：不需要记得手动跑 guideline 检查和金额审查，工作流自动串进来了。
4. **全程一条命令**：从分析到实现到检查，不需要人工在中间切换 skill 或判断下一步该做什么。

|---|---|---|
| 团队标准开发流程 | 把 Superpowers 的开发规范和内部规则组合成固定流程 | 需要先选一个高频流程跑通 |
| 新项目初始化 | 通过插件和模板快速获得 workflow 能力 | 模板中的占位 skill 要替换为当前环境可用 skill |

## ✅ 心得与经验

### 有效做法

1. **把 Superpowers 当作规范来源，不是终点**  
   Superpowers 提供好的开发动作，WeaveSpec 要做的是把这些动作编排成团队可复用流程。

2. **先选高频流程，而不是一上来编排所有事**  
   API 开发、后端功能开发、内容发布、专项审查这类高频稳定流程更适合先落地。

3. **每个 step 尽量只做一件事**  
   一个 step 对应一个职责清楚的 skill。步骤越清楚，替换和 A/B 对比越容易。

4. **gate 只放在关键点**  
   方向分叉和不可逆动作前需要人工确认；普通中间步骤不要频繁打断。

5. **保留运行记录**  
   失败后先看 `state.yaml` 和 `step-*.output.md`，再决定改哪个 step。

6. **改 workflow，不要只改单次输出**  
   单次手修只能救这一轮，调整 workflow 才能让后续所有运行受益。

### 注意事项

1. **不要把 WeaveSpec 写成“复用 Superpowers”**  
   这个项目的核心是编排层、状态层、对比层和分发层。

2. **不要把 workflow 当成超长 Prompt**  
   Workflow 是步骤、依赖、状态、gate 和输出的组合，不是把提示词叠长。

3. **不要忽略 validator**  
   YAML、skill 引用、DAG 和 gate 配置需要校验，否则流程会变成不可运行文档。

4. **不要用不同输入做 A/B 对比**  
   输入不同会让对比结论失真，无法判断差异来自 skill 还是输入。

### 可复用流程

1. 找一个高频、重复、边界清楚的工作流。
2. 列出已有可用规范和 skills，包括 Superpowers、内部 skill、专项审查 skill。
3. 把流程拆成 steps，明确每一步输入、输出和完成标准。
4. 用 `depends_on` 表达步骤依赖，而不是只写自然语言顺序。
5. 只在方向分叉和不可逆动作前设置 `user_confirm`。
6. 保存 workflow YAML，并用 validator 检查。
7. 运行后保留 state 和 step 输出。
8. 对效果不稳定的单步，用 `/workflow:compare` 做同输入对比。
9. 把改进写回 workflow 定义，而不是只修单次产物。

## 结论

WeaveSpec 的核心价值，不是提供另一个开发 skill，也不是简单复用 Superpowers。

它真正补上的，是 Superpowers 之外的四层能力：

- **编排层**：把多个 skills 和规范组织成 DAG workflow。
- **状态层**：保存运行记录，支持断点恢复和复盘。
- **优化层**：通过 Skill Swap 和 A/B compare 优化单步骤。
- **分发层**：通过 Claude Code plugin 和模板把流程交给团队复用。

从这个角度看，Superpowers 更像“开发规范库”，WeaveSpec 更像“团队 AI 工作流运行时”。
